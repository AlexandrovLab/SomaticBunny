# SomaticBunny regression tests

Small, deterministic tests for the parts of the pipeline that have had bugs before: the consensus
rules, panel-of-normals handling, VAF arithmetic and the structure of the final VCFs. Everything runs in
a minute on a laptop; no sequencing data and no database are needed.

## What is covered

| File | Guards against |
|---|---|
| `test_consensus.py` | wrong scenario membership (1 vs 2 PASS callers), equivalent indel spellings counted twice, duplicate records within one caller counted twice, an empty caller file breaking the run, panel-of-normals veto (`-p`), scenario 6 threshold demotion and rescue, MNV decomposition, multi-allelic splitting, viral / chrM / unplaced contigs entering the consensus, `--callable_bed` and `--consensus_contigs` restriction, a BED edge shifted by one base (0-based half-open BED vs 1-based VCF POS) |
| `test_vcf_structure.py` | scenario and final VCFs that htslib cannot parse, INFO keys used but not declared, unsorted or incomplete final VCFs |
| `test_vaf.py` | wrong SNV or indel counts and VAFs, loci files with duplicates, schema drift of the VAF table |
| `test_static.py` | shell, Python and YAML syntax; `-pon` passed without a panel; outputs anchored to `projectDir`; consensus default region set |
| `test_nextflow.py` | `main.nf` and every module compile (`-preview`); RN7 refused without opt-in and run without `-pon` with it; invalid `--first_step` and bad sample identifiers refused; outputs under the launch directory |
| `test_production_envs.py` | the tools the tests launched are not the production versions pinned in `yml/POST.yml` and `yml/alleleCounter.yml` (only with `SB_PRODUCTION_ENVS=1`, see below) |

Inputs are generated by `make_fixtures.py` from a seeded random reference (24 tiny primary
chromosomes, `chrM`, `HPV16`, an unplaced contig), five caller VCFs in each caller's own layout and two
BAMs with known REF/ALT read counts. The `CASES` table in that file is the single source of truth for
every expectation.

## Running locally

```bash
conda env create -f tests/environment.yml                  # python 3, bcftools, samtools, pysam, pytest, nextflow
conda env create -f tests/environment-biasfilter.yml       # python 2.7 for the DKFZ bias filter (scenario 6)
conda activate somaticbunny-tests
git clone https://github.com/DKFZ-ODCF/DKFZBiasFilter tests/_deps/DKFZBiasFilter   # or SB_DB=/path/to/database
SB_BIASFILTER_PYTHON=$(conda run -n somaticbunny-biasfilter which python) pytest -v tests
```

The pinned bias-filter commit is Python 2 code, hence the second environment; `conftest.py` probes it
once and skips the scenario 6 tests with the reason if it cannot run (CI treats that skip as a failure).
Without `nextflow` on the PATH the preview tests are skipped. On TSCC, `SB_DB=$DB` makes the tests use
the database's own copy of the bias filter.

## Running against the production environments

The pipeline runs the consensus step in `yml/POST.yml` (Python 2.7, bcftools 1.9) and the VAF step in
`yml/alleleCounter.yml`. To run the tests with exactly those tools, create the two environments from the
pipeline's own files and point the tests at them:

```bash
conda env create -f yml/POST.yml                           # name: POST
conda env create -f yml/alleleCounter.yml                  # name: alleleCounter
conda activate somaticbunny-tests
export SB_TOOLS_BIN="$(conda run -n POST printenv CONDA_PREFIX)/bin:$(conda run -n alleleCounter printenv CONDA_PREFIX)/bin"
export SB_BIASFILTER_PYTHON="$(conda run -n POST which python)"
export SB_VAF_PYTHON="$(conda run -n alleleCounter which python3)"
SB_PRODUCTION_ENVS=1 pytest -v tests/test_consensus.py tests/test_vcf_structure.py tests/test_vaf.py tests/test_production_envs.py
```

`SB_TOOLS_BIN` is put in front of `PATH` for every pipeline tool the tests launch (`bcftools`,
`alleleCounter`, ...); the two interpreters are passed explicitly because the two environments have
different Pythons. `SB_PRODUCTION_ENVS=1` makes `test_production_envs.py` assert that the versions in use
are the ones pinned in `yml/`. On TSCC the environments Nextflow already created can be used instead of
creating new ones (`conda env list`).

## Continuous integration

`.github/workflows/ci.yml` runs three jobs on every pull request and on pushes to `main`:

- `lint`: shell, Python and YAML syntax and the static invariants;
- `tests`: the full suite with current tool versions (`tests/environment.yml`);
- `production-envs`: the consensus, VCF structure and VAF tests with environments created from
  `yml/POST.yml` and `yml/alleleCounter.yml`, with `test_production_envs.py` proving which versions ran
  and no test allowed to skip.

A pull request that breaks a consensus rule, declares an INFO key wrongly, changes a VAF count, makes
`main.nf` fail to compile, or stops working with the production bcftools or Python turns red.
